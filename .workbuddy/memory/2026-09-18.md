## kvdb 项目启动：功能评估

用户提出用 Go 实现一个参考 RocksDB 的简单高性能 KV 存储，要求先做功能评估。

**已交付**：架构评估（3 张架构图 + 功能清单表 + 分阶段路线表）

**关键结论**
- 定位：单机嵌入式 / 单进程 / 不做分布式与事务
- 内核 6 个必需部件：WAL、MemTable、SSTable 文件格式、Manifest/Version、Compaction、internal key 编码
- 强调点：WAL 与 MemTable 是并行两条路；Immutable MemTable 必需（否则 flush 阻塞写入）；L0 区间重叠不可二分，L1 以下才可二分
- 强烈建议早期就做：Bloom Filter、Block Cache、WriteBatch、Snapshot/MVCC
- 明确初期不做：分布式/Raft、事务隔离级别、二级索引、多进程并发

**分阶段**：M0 骨架 → M1 最小可用（WAL+MemTable+简单 SST+恢复）→ M2 读优化 → M3 写优化（Compaction+Manifest）→ M4 一致性 → M5 生产化

**参考实现**：cockroachdb/pebble（最值得读）、dgraph-io/badger、LevelDB table_format 文档

## M1 最小可用：已实现并验收通过

验收标准「单线程 10 万次读写结果正确；kill -9 后数据不丢」两条都达成。

**验收结果**：gofmt -l / go vet / GOOS=linux go build 均无输出；测试函数共 101 个全 PASS；
覆盖率 kvdb 89.3%、key 98.1%、memdb 100.0%、wal 85.1%、sst 80.5%。

**关键实现决策（详见 DESIGN.md 9.9）**
- 恢复时强制把重放结果落成 SST 再删旧日志，删日志判据 = 编号 < min(mem.logNum, imm.logNum)
- 崩溃中断的 Flush（footer 不全的 .sst）直接删除，数据仍在 WAL 里
- 目录锁用 OS 级锁而非 O_EXCL 锁文件（否则 kill -9 后目录永久打不开）
- 同一时刻只允许一张 Immutable；写者在冻结时最多等它落盘
- 序列号写进 WriteBatch 头部，恢复时原样沿用（绝不能重新分配）
- Close 不落盘 MemTable，下次 Open 走"重放 + 落盘"，让恢复路径每次都被走到
- 日志尾部损坏可容忍、文件中段损坏不可容忍
- 文件编号在 SST 与日志之间共享，`编号大 = 更新`

**崩溃测试的做法（重要）**：同进程内"不调 Close"证明不了什么（目录锁要进程真的死才释放）。
用 `exec.Command(os.Args[0], "-test.run=TestCrashWriterChild")` + 环境变量传参，
子进程写完 `os.Exit(1)` 不做任何清理；父进程重开校验。
另有一条用例在子进程里直接往日志尾部追加 3 个垃圾字节，验证半截记录被容忍。

**性能观感（cmd/kvdb-bench，SyncWrites=false）**：写完 5.54 µs/op；
但 3 个 SST 时读只有 3930 ops/s（254 µs/op）——线性扫描的代价，正是 M2 的靶子。

**环境新增经验**
- PowerShell 里跑 go 命令要先把 `[Console]::OutputEncoding` 设为 UTF-8，否则中文输出变乱码
- 已固化为 `scripts/gotest.ps1`（用法：`powershell -NoProfile -File scripts\gotest.ps1 test ./... -cover`，结果写在 `_t.log`）
- 批量替换重复代码片段时，Edit 工具的 replace_all 比 PowerShell 正则替换可靠（正则只命中了一部分，还静默返回成功）

**下一步（M2）**：internal/filter（Bloom）、internal/cache（分片 LRU）、sst 改成 Data/Index/MetaIndex/Footer 五段式、
internal/iterator（MergingIterator）、db 的 NewIterator/GetSnapshot。见 DESIGN.md 9.10。

## 打通 cgo / -race（把 M0 遗留的最大风险项清掉）

用户提示本机已装 msys2 + gcc，实测确认并跑通了 `-race`。

**环境事实**
- MSYS2 装在 `C:\msys64`；gcc 16.1.0 在 `C:\msys64\ucrt64\bin\gcc.exe`
  （只有 UCRT64 装了 toolchain，mingw64/mingw32/clang64 都没有 gcc）
- gcc 不在系统 PATH 里；`go env CGO_ENABLED` 默认 0
- 验证用最小 cgo 程序（C 里 `printf("hello from C")`）→ `go run` 打印成功，`go build -race` 成功

**关键发现：只有 Bash 工具跑得通 cgo**
- PowerShell 工具里改 `$env:PATH` 不会传给子进程（实测子进程看到的仍是旧 PATH），
  连 `CC=<gcc 绝对路径>` 也在 cgo 阶段报 `cgo.exe: exit status 2` —— 在 PowerShell 里 cgo 无解
- Bash 工具里 `export PATH=...` 能真正传给子进程；虽然 coreutils（ls/sed/which）全缺，
  但 echo/cd/export/重定向可用，跑 go 命令完全够用

**可用配方**
```bash
export PATH="/c/msys64/ucrt64/bin:$PATH"
export CGO_ENABLED=1 CC=gcc
cd /c/Users/summer/repos/kvdb
"/c/Program Files/Go/bin/go.exe" test -race ./... > _race.log 2>&1
```

**验收结果**：`ok kvdb 12.617s`，key/memdb/sst/wal 四个内部包全 ok，race_exit=0，**无 data race 报告**。
M1 的并发代码（跳表、后台 Flush、Immutable 冻结）通过竞态检测，DESIGN.md 里"留到 M4 补验"的
`-race` 项可以提前划掉。

- `internal/iterator/`：iterator.go（统一接口）、merging.go（最小堆归并）、dbiter.go（可见性/墓碑/去重/闭区间边界）

- 测试：crc_test / filter_test / lru_test / block_test / sst_test(重写) / iterator_test / db_iter_test

**验收结果**
- `go test ./... -count=1 -cover` 全绿：kvdb 89.6%、cache 96.8%、crc 100%、filter 94.4%、iterator 86.1%、
  key 98.1%、memdb 98.6%、sst 79.5%、wal 84.9%
- `go vet ./...` / `gofmt -l` 无输出；`go test -race ./...` 全绿，无 data race
- 基准（10 万 key、value 100B）：4 个 SST 时 get(hit) 2.83 µs/op、顺序读回 1.72 µs/op、
  范围扫描 0.06–0.15 µs/key、缓存命中率 89.2%
- **与 M1 同口径对比**：M1 三个 SST 时读回 254 µs/op → M2 四个 SST 时 1.72 µs/op，约 **148 倍**
- **文件数扫描（`-mode sweep`）**：文件数 ×69、get(hit) ×4.4；拟合 `≈ 2.22 + 0.126 × files` µs。
  对照组关掉 Bloom 与缓存后线性项系数 2.354 µs/文件（差 18.7 倍），69 文件时 168.11 µs vs 11.17 µs

**关键实现决策（详见 DESIGN.md 9.13）**
- 同一 user key 的所有版本必须落在同一个 Data Block 里（块边界只在 user key 变化时切）——
  这是"读一块就能定可见版本"的正确性前提
- Bloom 建在 **user key** 上，不是带 `(seq, type)` 后缀的 internal key
- Filter Block 解析失败时返回"可能存在"，绝不返回"肯定不存在"（过滤器坏了不能变成静默丢数据）
- Index 记的是块的 **max key**（不是首 key），与 LevelDB 一致
- 缓存键必须带 fileNum：文件编号会因删除而复用，只用 offset 会串味
- 分片哈希用 splitmix64 fmix 打散**对齐后**的偏移（块偏移都是 4KB 对齐，直接取低位会全落一个分片）
- `DB.Get` 出口统一 `copyValue` —— 返回的切片可能指向块缓存内部字节
- magic 从 `kvdb0001` 升到 `kvdb0002`；旧文件报 `ErrLegacyFormat` 且**不可容忍**（不能当损坏文件删掉）
- `scanSSTFiles` 的丢弃判据收紧到只有 `ErrBadFooter` / `ErrCorruptBlock`
- 迭代器接口现在就把 `Close()` 放进去（M3 版本引用计数后才是必需的）

**验收里最容易被误读的一点（重要）**：sweep 的曲线**不是平的**。M2 没有 Compaction，L0 文件数无上限，
所以"每文件一次元数据探测"的线性项（0.126 µs/文件）客观存在，要等 M3 的 `L0CompactionTrigger` 才被兜住。
变的是**量级**：从"每文件一次全文件扫描"降到"每文件一次 Bloom 判定"，约三个数量级。
文档里按这个口径写，没有说成"延迟与文件数无关"。

**基准工具的新用法**：`-mode` 取 `all | write | point | scan | sweep`；`sweep` 默认带一组
"关掉 Bloom 与缓存"的对照（`-variants=false` 可关）。`get(hit)` 与 `get(miss)` 分开报，
因为 Bloom 的价值只体现在负向查询上。写完后会等 Immutable 落盘再测读，否则测到的还是 MemTable。
